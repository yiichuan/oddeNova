# 曲子编排（Song Arrangement）设计

**日期**: 2026-06-19
**状态**: 已实现（Phase 1，prompt v17 + parser envelope）。本文档含真机测试后的多轮迭代。

## 背景与问题

当用户的输入导向"让 agent 一次性写一首完整的曲子"时，当前 agent 容易产出**某些层一直循环不变**的结果：整首曲子的鼓节奏一成不变，没有错开/入场/出场的编排，听感上是乐器一直在叠加，而没有延伸出一首完整的曲子。这种做法适合 live coding，但不适合更广阔的其它类型风格的曲子。

**根因**：agent 始终输出 `setcps(N)` + `stack(layerA, layerB, ...)`，每一层从 cycle 0 开始永远同步循环，没有任何时间编排原语。[parser.ts](../../../src/agent/parser.ts) 也假设这种单一 `stack` 结构；当前 prompt v16 的"音层代码生成"节只讲频率分区和密度，从不涉及层如何随时间演进。"乐器叠上去就永不离场"被同时固化在 prompt 和工具里。

## 已确定的决策（来自 brainstorm）

1. **触发方式：按意图智能判断。** 默认行为不变；只在判断到"完整曲子"意图时升级为带编排的生成。
2. **编排深度：两者结合，分阶段。** Phase 1 用层级包络解决 80% 问题（保持单 stack）；真·多段落 `arrange()` 留给 Phase 2。
3. **时间形态：长弧形循环。** 依然无限循环，但在一个窗口（迭代后约 8/16 cycle，入场前置）内走出 intro→build→main→breakdown→return 的弧线，然后重复。**不改 strudel 播放/导出逻辑。**
4. **Phase 1 范围：A（新 prompt v17）+ C 的摘要部分（parser 在摘要中显示每层编排包络）。** 不做编排 lint（B）。

## 核心机制

### 概念：层级编排包络

"编排包络"指**一整个乐器层在整首曲子的若干 cycle 内如何随时间变化的轮廓**（区别于单音符内部的 ADSR 音量包络）。两类手段：

- **门控（硬切进出）**：`.mask("<1 0 1 1>/N")`
- **渐变（平滑淡入淡出 / 扫频）**：`.gain("<0 0 .3 .5>/N")`、`.lpf("<400 800 2000 4000>/N")`

例如主奏层 `.gain("<0 0 .3 .5>/16")`：把 16 cycle 切成 4 段（每段 4 cycle），音量依次 `0→0→0.3→0.5`，即前 8 cycle 静默、后半段才缓缓淡入。

把编排拆成两个相互独立的概念——一个负责"长弧线"，一个负责"不死板"。两者都靠现有 cheatsheet 已有的原语实现，**不引入固定模板骨架**。

### 概念一：编排网格——只管入场/出场，拉出长弧线

用 `.mask(...)`（硬切进出）或大尺度 `.gain(...)`（淡入淡出）决定**每层何时进入、何时退出**，让整首走出 intro→build→main→breakdown→return 的弧线。这些"进出包络"应共用同一窗口（如都用 `/16`）、边界对齐，否则各层进出错位听感会乱。

- 段数**不固定为 4**：可 2/3/4，可再细分（如 `<[0 1] 1 1 1>`）、可用 `.early()/.late()` 错位。
- 错开原则：不是所有层从 cycle 0 全开；鼓骨架先入，贝斯/和声/主奏依次进入，某些层在 breakdown 段退出。
- **前置入场（迭代加入）**：时长只决定整首多少 cycle，**不是入场跨度**。核心层要在**前 ~8 cycle（intro/build）内进齐**，任何核心层（尤其贝斯/主旋律）不要过半才首次出现；进出窗口用常规 `8`/`16`，**不用 32+**。入场时刻按公式算：`<v1…vk>/N` 每段 `N/k` cycle、第 m 段从 cycle `(m-1)·N/k` 起。后段（breakdown/outro）才用退出制造起伏。

### 概念二：段落级内容变化——层不止"开/关"（迭代加入）

进出包络只能控制一层"响/不响/多响"，改不了它的内容。但真实歌曲段落之间常有鼓组/旋律切换。所以层可在**段落网格（约 8 cycle/段 = 常规一个段落）**上用 `<内容A 内容B …>/N` 写进 `s(...)`/`note(...)`/`n(...)`/`.struct(...)`/`.bank(...)`，让鼓点/旋律/音色在段落间切换（主歌四踩→副歌加密→breakdown 前 fill→bank 909→808）。

- 与「概念一」分工：**入场细粒度、前 8 cycle**；**段落内容切换走较粗的 8 cycle/段网格**，两套网格边界对齐、互不打架。
- 定位为**按音乐需要使用的可选手段**，**不是**"每层切等长 N 段、每段都不同"的硬模板——避免回到千篇一律的方块结构。
- 历史注记：早期 spec 曾删除此机制（连同 coastline 范例），因担心"四段内容全变"诱导同质化；真机测试暴露"鼓组整首不变、只有进出"的缺陷后，以"可选原则"的措辞重新加回。

### 概念三：微观变化——让内容"活"，避免机械循环

层**内部**的节奏/音色/调制要刻意制造永不齐刷刷重复的细碎变化。手段（均来自现有 cheatsheet）：

- **混合周期**：同一层里用不同长度的 `<...>` 交替（2/4/8 cycle 混用），使各周期的最小公倍数很长，组合起来长时间不重复。例：`struct("<[x*<1 2> [~@3 x]] x>")`。
- **连续信号**：`sine/perlin/rand` 配 `.range(a,b).slow(N)` 调制 gain/lpf/pan/fm，曲线连续、永不精确重复。
- **随机/条件变换**：`.sometimes(...)`、`.rarely(ply("2"))`、`.chunk(N, fast(2))`、`.degradeBy(...)`。

> 关键：长弧靠「概念一」的进出包络（且入场前置），段落对比靠「概念二」的内容切换，活力靠「概念三」的微观变化。三者都是**按需组合的原则**，**绝不**强制把整首压成"每段等长、每层都切 N 段且各不同"的方块结构——那是另一种死板。

### 原则而非模板

v17 把编排教成**一套可自由组合的原则**，而不是一段可照抄的模板骨架——窗口长度、段数、入场顺序、门控 vs 渐变、用哪几种微观变化手段，都由 agent 按风格与情绪自选。这样既避免逐字模板诱导出千篇一律的结构，也让实现时不会把某个具体写法固化进 prompt。

## 方案 A：Prompt v17

遵循 [.github/prompts/edit-system-prompt.prompt.md](../../../.github/prompts/edit-system-prompt.prompt.md) 规范：新建 `src/prompts/versions/v17.ts`（**不改任何旧版本**），更新其头部注释，把 `src/prompts/active.ts` 指向 v17，**不动** `system-prompt.ts`。中英双语同步修改（`AGENT_SYSTEM_PROMPT_OPENAI` 与 `AGENT_SYSTEM_PROMPT_EN`）。

已落地的 v17 在现有"音层代码生成 / Layer code generation"节之后追加「曲子编排 / Song arrangement」节，并在工作流程、提交前自检、规则三处各加一条。中英双语同步。要点（以下为真机测试后的最终形态）：

1. **意图判断 + 何时启用**：从零创作且用户偏"作品"（风格名、"一首/完整/song/track"、给了时长、或描述情绪旅程/段落）→ **必须**编排。jam（"加个 bass""来点鼓"）或**编辑现有代码** → 不强加编排。

2. **❗硬性最低要求（完整曲子必须全满足，否则视为未完成）**：
   - 至少 2–3 个主要层带进出包络（`.mask("<...>/N")` 或大尺度 `.gain("<...>/N")`），不同时间进出、共用窗口对齐；**禁止所有层固定常数 gain 响到尾**。
   - 至少 1 层用连续信号调制（`.lpf(sine.range(...).slow(N))` / `.gain(perlin.range(...))`）。
   - 错开入场**且前置**：核心层在前 ~8 cycle 进齐。

3. **前置入场（迭代）**：时长 = 总长，不是入场跨度（cycle/分钟 ≈ `cps×60`）。核心层前 8 cycle 进齐，鼓 0 / 贝斯 ~2–4 / 和声 ~4 / 主旋律 ~8 / 点缀 ~8–12；窗口用 `8`/`16`，不用 32+。给出段长公式：`<v1…vk>/N` 每段 `N/k` cycle、第 m 段从 cycle `(m-1)·N/k` 起。

4. **段落级内容变化（迭代加回）**：层可在约 8 cycle/段的段落网格上用 `<内容A 内容B…>/N`（写进 `s()`/`note()`/`.struct()`/`.bank()`）切换鼓点/旋律/音色；定位为按需可选手段，非"每层切等长 N 段"。详见上文《概念二》。

5. **微观变化**：层内部混用不同周期 `<...>` 交替（2/4/8）+ 连续信号 + 随机/条件变换（`sometimes/rarely/chunk/ply/degradeBy`）。原语 cheatsheet 已有，无需新增语法。

6. **原则而非模板**：窗口长度/段数/入场顺序/门控 vs 渐变/微观手段都按风格情绪自选，不套固定骨架。

7. **工作流程**步骤 1「若无现有代码」追加"规划编排"；**提交前自检**追加"这是完整曲子吗？各层是否错开入场/出场+微观变化"；**规则**追加**编排阻断**：完整曲子意图下若各层全固定 gain、无任何进出包络，`commit` 前必须先补齐硬性最低要求。

**写法约束**：v17 用**原则性语言 + 极简语法示意**，**不放可整段照抄的模板或具体范例曲**（如 coastline）——逐字范例会诱导同质化输出。任何示意中的 `<...>/N` 与采样/bank 名称必须能通过现有 `validate`，名称取自 `sample-allowlist.ts`。prompt 只在意图判断为"完整曲子"时启用编排。

## 方案 C（摘要部分）：parser 感知编排包络

让结构解析器看懂每层的编排包络，并写进给 agent 的"当前代码摘要"，使多轮编辑不丢失编排。

### 数据结构

[parser.ts](../../../src/agent/parser.ts) 的 `ParsedLayer` 新增可选字段：

```ts
export interface ParsedLayer {
  name: string;
  source: string;
  rawStart: number;
  rawEnd: number;
  envelope?: string;   // 人类可读的编排描述，无包络时 undefined
}
```

### 提取逻辑

在 `parseScore` 构造每个 layer 时，从 `source` 提取带 `<...>/N` 的循环窗口（出现在 `.mask(...)`、`.gain("<...>/N")`、`.lpf("<...>/N")`、`s("<...>/N")`、`.bank("<...>/N")` 等处），归纳成**语言中立的 `role/N` 列表**（如 `"mask/16 gain/16"`），role 取方法名本身。无任何此类标志时 `envelope` 留 `undefined`。**只识别带 `/N` 的慢化交替**（arrangement 尺度）；不带 `/N` 的逐 cycle `<a b>` 属微观变化，刻意排除。

实现要点（已落地）：用单条正则 `\.?(mask|gain|lpf|hpf|bank|note|struct|n|s)\s*\(\s*["'`+'`'+`][^"'`+'`'+`]*?<[^>]*?>\s*\/\s*(\d+(?:\.\d+)?)` 在已切出的 `source` 上匹配方法名 + 窗口 N，去重后用空格连接。提取**保守且无副作用**——无匹配返回 `undefined`，绝不抛错或改变现有解析行为。语言交给消费方（loop.ts）按 `isZh` 渲染。

### 摘要输出

`summariseScore` 在每层 `preview` 后追加 envelope（仅当存在）：

```ts
layers: score.layers.map((l) => ({
  name: l.name,
  preview: l.source.length > 80 ? l.source.slice(0, 77) + '...' : l.source,
  envelope: l.envelope,   // 新增，供系统消息摘要展示
})),
```

消费方是 [loop.ts:143-147](../../../src/agent/loop.ts#L143)：构造"当前正在播放的代码"系统消息时，目前 `layers` 只渲染了 `l.name`（`layers.map((l) => l.name).join(' / ')`），完整代码本身也已注入到消息的代码块里。在该 `layers.map` 处把 envelope 拼进每层标签（仅当存在），例如 `drums[进出/16] / bass / pad`，作为给 agent 的注意力提示——让其编辑时主动保留/呼应既有编排。中英两个分支（`isZh`）都要改。

> 说明：因完整代码已在系统消息中注入，agent 本就能读到 envelope；此处摘要展示是把编排显式抬到层标签上，强化"编辑时别抹平编排"的注意力，改动小、收益确定。

## 测试

按 CLAUDE.md 要求，与 parser 改动同一 commit 更新 [parser.test.ts](../../../src/agent/__tests__/parser.test.ts)：

- 含 `.mask("<1 0 1 1>/16")` 的层 → `envelope` 非空且包含 `16`、`mask`。

- `summariseScore` 输出在有包络时包含 envelope 文本、无包络时不含。

## 实现与迭代记录

按计划实现后，又据真机测试做了三轮 prompt 迭代（均直接改 v17，应用户要求）：

1. **基线实现**（`b7a1e57`）：parser envelope 字段 + 摘要渲染 + 测试；prompt v17 编排节（原则版）。
2. **硬约束化**（`7e9f1c8`）：真机测试"乡村流行 1 分钟"产出 5 个静态层、零编排——把编排从建议升级为**硬性最低要求** + **时长→窗口换算** + **commit 阻断规则** + 工作流程规划步骤。
3. **入场前置 + 收窄窗口**（`690b694`）：再测发现编排生效但主旋律过半才进、班卓 3/4 才进、`/32` 窗口太粗——明确**时长=总长非入场跨度**、**前置入场到前 8 cycle**、窗口用 8/16、给出**段长换算公式**、后段留给 breakdown/outro。
4. **段落级内容变化**（`7b4d4c7`）：指出层只能开关、改不了内容（段落间换鼓组）——以"可选原则"措辞**加回段落级内容变化**（早期曾删除），并与前置入场分工（入场细/段落粗）。

## 明确不做（留给 Phase 2）

- `arrange()` 真·多段落（verse/chorus 不同**结构/乐器集**）、parser 多-stack 支持。
- 编排 lint（方案 B：在 commit 前检查 agent 是否真的做了编排）——因其需要猜测意图、阈值脆弱。
- 有限、会自动结束的曲子（需改播放/导出逻辑）。
- UI 模式开关（完整曲子模式 vs live coding 模式）。

## 验收标准

- 输入"写一首完整的 lo-fi house"这类完整曲子意图 → 各层有错开的进出包络（共用窗口、对齐）拉出弧线，≥1 层连续信号调制，**核心层在前 ~8 cycle 进齐**（主旋律不晚于过半），内部有微观变化，通过 `validate`。
- 给了时长（"一分钟左右"）→ 时长换算为总长而非把入场摊到全曲；窗口用 8/16 而非 32+。
- 需要段落对比时 → 可用段落级内容变化让鼓点/旋律在段落间切换，但不强制每层都切。
- 输入"加个 bass""来点鼓"等 jam 意图，或编辑现有代码 → 行为与 v16 一致，不强加编排。
- 对一首已带编排的曲子做增量编辑（如"把鼓调小"）→ 系统消息摘要里能看到既有 envelope，编辑后其它层的编排不被抹平。
- parser 新增 envelope 提取无副作用，现有测试全绿，新测试覆盖上述场景。
