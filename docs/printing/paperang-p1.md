# 喵喵机 P1 分享二维码打印

目标环境为 macOS Chrome、HTTPS 页面和暴露下述 BLE 服务的喵喵机 P1。二维码编码与纸条位图在本地生成，分享仍使用 `/api/share`。当前仅实现网页 BLE 直连；经典蓝牙入口不受支持，需要另行实现本地桥接。

## 已知连接限制

实机反馈出现 `NetworkError: Unsupported device.`，失败阶段为蓝牙连接。Chromium 的 macOS 经典蓝牙设备实现会直接拒绝 GATT 连接并返回此错误，见 [Chromium 源码](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/device/bluetooth/bluetooth_classic_device_mac.mm)。这说明所选入口不能通过当前 BLE 路径连接，不能据此断言硬件没有独立 BLE 入口。

2026-10-14 原生 CoreBluetooth 诊断发现名为 `MiaoMiaoJi` 的可连接 BLE 广播，用户确认型号为 P1。成功连接并发现 `FF00` 服务、`FF01`（notify）、`FF02`（write / writeWithoutResponse）、`FF03`（write / notify）。向 `FF02` 发送默认 CRC 种子的 P1 电量查询 `021000010001d0b959e903`，`FF01` 返回 `02110001003eed943f5f0302100001000046895e9e03`，包含电量值 62，之后已断开。未发送图片、走纸或配置修改指令。

网页选择器现在按支持的 BLE 服务筛选，`FF00` 同时限制名称前缀为 `MiaoMiaoJi` 或 `Paperang`，避免将同名经典蓝牙入口或无关设备作为候选。仅当旧服务发现返回 `NotFoundError` 时尝试 `FF00 / FF02`，连接中断或权限错误不触发服务切换。这仍是 BLE 直连；若确为仅经典蓝牙型号，需明确选择本地桥接方案后另行实现。

网页连接成功后，实机反馈约 490 字节的响应写入卡住并最终中断。原生诊断读取到 CoreBluetooth 的最大写入长度：有响应 512 字节、无响应 20 字节；宿主报告的响应写入上限并不证明设备能正确处理长写入。将同一电量查询分成无响应小包后成功返回电量 61。`FF03` 通知 `01 04` 提供初始 4 包发送额度，后续 `01 01` 每次补充 1 包额度；`02 67 00` 等其他通知不作为发送额度处理。进一步将电量查询拆为 11 个单字节包，按此额度等待和补充，仍得到有效 P1 回复。

`FF00 / FF02` 的网页传输现在将完整 P1 帧拆成最多 20 字节的小包，使用无响应写入并订阅 `FF03` 控制缓冲额度。旧 ISSC 通道仍按完整帧响应写入。所有写入、通知订阅及额度等待有 10 秒超时；失败后断开连接，不自动补发，并在界面显示失败帧、字节偏移和错误详情。原生诊断没有打印二维码，网页出纸仍需人工验收。

后续网页反馈在第 1 帧、第 80 字节发生额度等待超时，即初始 4 个 20 字节包耗尽。原生对照复现：仅订阅 `FF03` 时，11 个单字节查询包同样在第 4 包后停住，没有补充额度；此前同时订阅 `FF01` 和 `FF03` 的诊断则正常完成。连接初始化已补充先订阅 `FF01` 接收通知，再订阅 `FF03` 流控通知。订阅 `FF01` 是此 P1 开启完整串口通道、持续获得发送额度的前提，不能仅把它当成可选的响应显示通道。

## 人工验收

当前代码已加入自动化验证，原生诊断已完成 BLE 连接和电量查询；网页内连接、出纸和扫码仍未完成验收。禁止将单元测试、原生查询或构建成功描述为完整硬件打印兼容性验证完成。

1. 开启 P1，关闭官方 App 等可能占用连接的应用。在 macOS 隐私设置中允许 Chrome 使用蓝牙。
2. 用 Chrome 打开 HTTPS 部署，打开任意作品并点击分享。确认标题、二维码、链接和 30 天有效期提示；生成预览时不应弹出设备选择。
3. 点击“连接打印机”，在系统选择器中选 P1。若取消，面板保留且不显示错误。连接失败时记录界面提示阶段（选择设备、蓝牙连接、发现 P1 服务、发现打印通道）、浏览器详情中的错误名和原始消息、P1 版本、macOS 与 Chrome 版本。服务发现阶段的 `NotFoundError` 表示 GATT 已连接，但未找到指定服务；不能仅凭设备名称确认兼容性，也不能统一归因为未开机或权限问题。未验证前不增加其他连接方式作为隐式回退。
4. 连接成功后点击“打印一份”。确认纸条有最多两行中文标题、完整二维码、oddeNova 字样，走纸足够撕取且不裁切二维码白边。界面仅承诺“已发送至打印机”，不代表已检测到物理出纸。
5. 用手机扫码，确认打开的是该次分享的作品快照，且二维码内容与面板复制的 URL 完全一致。
6. 关闭面板，分享另一首作品。无需重新选择设备，能打印新二维码；两张纸条分别打开正确作品。
7. 补打同一面板的纸条：链接不变，不产生额外分享上传。修改作品后关闭再打开面板：生成新的分享快照。
8. 测试打印中快速重复点击、关闭面板、P1 断电及重新开机。中断后不自动重打，可能已部分出纸；确认纸条后手动重连补打。
9. 用长中文标题检查两行换行与省略号，用普通手机在现场光线下扫码。检查桌面和手机的面板视觉布局、键盘 Tab、Escape 和关闭后焦点恢复。

## 实现边界

- P1 打印宽度为 384 点，黑点按高位优先打包为每行 48 字节；一帧最多包含 10 个完整像素行。BLE 传输分片可以跨行，重组后的 P1 帧内容和 CRC 保持不变。
- 协议编码、CRC32 校验和蓝牙传输相互隔离。参考协议观察来源：<https://github.com/Yrr0r/paperang-web>。没有复用该项目的 UI 或代码。
- 支持 BLE 服务 `49535343-fe7d-4ae5-8fa9-9fafd205e455` 与写入特征 `49535343-6daa-4d02-abf6-19569aca69fe`，以及本次原生查询验证的 `0000ff00-0000-1000-8000-00805f9b34fb` 与写入特征 `0000ff02-0000-1000-8000-00805f9b34fb`。其他硬件/固件版本仍需实机确认，不能仅凭通用 `FF00` UUID 判定协议兼容。
- 浏览器连接参考：<https://developer.chrome.com/docs/capabilities/bluetooth>。设备选择必须由点击直接触发，候选设备按上述 BLE 服务筛选。
- 页面内保持一个打印机连接，面板关闭不会断开；刷新后需重新连接。不持久化设备 ID，不把作品名、链接、纸条或设备信息发送给统计服务。
- 打印事件 `share_print_finished` 仅记录 `sent` / `failed`；二维码预览和数据发送不计入已有的 `share_completed`。
- 分享内容按现有清理策略约 30 天后失效；不改后端清理或保存策略。
